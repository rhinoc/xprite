# 微信版本与网页版一致性要求

## 必须达到的结果

以当前网页版为参照，在相同内容视口尺寸、语言、主题、UI 缩放、文档与设置下，小程序应提供相同功能、界面布局、控件顺序、菜单、对话框、操作流程、默认行为和编辑结果。使用微信官方规定的原生入口替代无法提供的浏览器能力时，保留原入口所属菜单及产品语义。

不能把缺少功能归因为“首版”、实现成本、库缺陷或自行选择的容量上限。代码复用只是实现方法，不能代替实际验证。

## 当前差距

| 范围                       | 网页实现来源                                             | 现有原型情况                             |
| -------------------------- | -------------------------------------------------------- | ---------------------------------------- |
| 完整应用与文档工作区       | `apps/editor/src/App.tsx`、`managers/workspace`          | 使用独立单文档管理器，尚不一致           |
| UI 控件与皮肤              | `packages/ui`、`packages/editor-ui`                      | 使用微信默认按钮与新布局，尚不一致       |
| 菜单、工具、状态栏         | `components/shell`、`components/tools`                   | 仅提供部分入口，尚不一致                 |
| 选择、文字、滤镜、文档属性 | 对应组件、管理器及 editor-core 公开 API                  | 核心已有能力，原生入口缺失               |
| 时间轴与图层完整操作       | `components/timeline`、`managers/timeline`               | 只有简化图层与帧控制，尚不一致           |
| 文件格式与导出设置         | `components/dialogs`、`managers/files`、编解码适配器     | 只有 Aseprite 与当前帧 PNG，尚不一致     |
| 设置与布局                 | `components/dialogs/preferences`、`managers/preferences` | 尚未接入                                 |
| 文档、帧、图层与文件上限   | editor-core 与网页相应策略                               | 原型自行收紧限制，最终实现须消除这些差异 |

这些差距均未获得官方限制豁免。

## 已调查的路径

腾讯维护的 [Kbone](https://github.com/wechat-miniprogram/kbone) 为小程序模拟 DOM/BOM，可运行 React。但检查其当前源码发现，直接运行现有 App 还不能满足要求：

- `miniprogram-render/src/node/element.js` 的同步 `getBoundingClientRect()` 是占位实现，只返回零坐标；实际几何查询通过异步 `$$getBoundingClientRect()` 提供。
- `miniprogram-render/src/window.js` 的 `getComputedStyle()` 没有实现；`$$getComputedStyle()` 是异步微信查询。
- `miniprogram-render/src/node/element/canvas.js` 的 `getContext()` 要求先异步调用 `$$prepare()`；现有 UI 同时使用立即可用的离屏 Canvas 与页面 Canvas。
- 网页的几何边界还依赖尺寸观察、滚动尺寸、命中查询及文字 Range。必须在原生边界提供可用语义，不能返回假尺寸让菜单、控件和绘画静默错位。

这些是待解决的适配工作，不是允许移除工具、对话框或重画简化 UI 的理由。候选适配路径必须先通过原生运行时检查，再决定共享 UI 的具体入口和边界改造，避免修改官网后才发现无法运行。

已准备独立运行时调查入口 `pnpm run wechat:probe`，只生成 `.tmp/wechat-runtime-probe`，不会覆盖原型或官网输出。它比较同步与异步的实际几何查询、Canvas 初始化和像素读回，并记录共享 UI 需要的浏览器接口是否存在。工程内的页面、控制台和本地键 `xprite:wechat:runtime-probe` 会显示调查结果。

用户已明确允许微信版本打包、运行及 UI 对比。2026-10-04 已在官方 ARM64 开发者工具 2.02.2608080、基础库 3.7.12、游客模式中打包并运行该工程。其结果仍不能代替完整功能或 UI 验收。

已实测通过的适配边界：同步离屏 Canvas、页面 Canvas 像素读回、真实几何与计算样式快照、120×40 到 160×40 的尺寸通知，以及使用相同 WOFF2 文件的中文字体加载。已直接运行 `@xprite/ui` 的按钮、复选框与共享皮肤；控件能够挂载和绘制，但文字布局、输入事件、CSS 选择器及所有控件的视觉一致性仍待验证。不能把“能绘制控件”标为完整 UI 等价。

当前仅进行了模拟器验证。账号尚未注册，因此未进行真机相册授权、文件转发或正式小程序环境验收。完整 App、工作区、菜单及文件流程尚未接入这条共享 UI 路径。

## 官方限制记录

目前已核实：[微信 web-view 文档](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)明确规定个人类型小程序不能使用该组件。因此个人主体版本需要原生渲染路径，不能将官网直接装入 web-view。这个限制不豁免任何绘画功能或 UI 一致性要求。

其他差异应逐条核实。原型的 512×512、64 帧、32 层、16 MiB 文件和 30 份作品上限均为实现选择，不能登记为官方限制。平台存储配额或画布 backing 尺寸也不能直接当作文档上限；需要先评估分块存储、视口渲染和编解码方案。

## 验收

- 同一作品进行相同绘画、选择、变换、文字、滤镜和时间轴操作，比较像素、文档结构、脏标记以及撤销/重做结果。
- 对照网页检查每个菜单、对话框、设置、快捷键及触摸入口；保留相同分组、顺序和应用/取消行为。
- 相同视口下比较首页、完整编辑器、菜单、对话框、时间轴、调色板以及明暗主题的截图与区域几何。
- 验证多文档切换、保存/另存为、所有已支持文件格式、导出选项、关闭取消、切后台及恢复。
- 在微信真机核对输入、权限、文件操作、存储不足和资源边界。无法验证的部分继续标为未验证，不能标为等价。

本次会话中，用户已明确授权微信版本的打包、运行与 UI 对比；该授权不改变官网构建、部署及像素校验规则。源码阅读与静态检查不能替代原生渲染验收。
